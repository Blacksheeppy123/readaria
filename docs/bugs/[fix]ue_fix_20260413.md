# iOS 无网络时 Feed 页误进入新人引导且播放列表无法访问

## 问题描述

- **什么功能出了问题**: iOS 设备在没有网络的情况下，Feed 首页和播放列表功能表现异常。
- **用户操作步骤**:
  1. 确保设备已正常登录并订阅过 RSS 源
  2. 关闭网络（飞行模式或断网）
  3. 重新打开 App 或刷新 Feed 页
  4. 进入"听一听"页面查看播放队列
- **实际表现**:
  - Feed 页直接显示新人引导流程（添加订阅源、导入 OPML 等），仿佛用户没有任何订阅
  - 之前加载过的文章列表消失，无法阅读已缓存内容
  - "听一听"播放列表/队列无法正常使用
- **预期表现**:
  - 应提示用户当前网络有问题
  - 应显示用户之前已经缓存的文章和阅读记录
  - 播放列表应保持可访问

## 原因定位

### 根本原因

1. **订阅源列表未做离线持久化**: `feedStore` 仅在内存中保存 `feeds` 数组，没有任何 `localStorage` 缓存。无网络时 `fetchFeeds()` 失败，`feeds` 为空，导致 `FeedView.hasFeeds` 为 `false`，触发新人引导 UI。
2. **文章列表未做离线持久化**: `FeedView` 和 `ArticlesView` 加载的文章只保存在组件内存 (`articles.value`) 中，页面刷新或重新打开 App 后全部丢失。无网络时 `getArticles()` API 调用失败，列表为空。
3. **播放文章时强依赖在线内容获取**: `playerStore.playArticle()` 在文章 `content` 为空时会调用 `getArticleByUrl()` 获取完整内容，离线时该请求失败，导致播放中断。
4. **Service Worker 未缓存 API 响应**: `vite-plugin-pwa` 的配置中，`/api/`、`/articles/` 等接口被显式列入 `navigateFallbackDenylist`，API 响应不会被 Service Worker 缓存。

### 相关代码位置

- `frontend/src/stores/feedStore.js` — `fetchFeeds()` 未缓存到本地
- `frontend/src/views/FeedView.vue` — `hasFeeds` 计算属性（约 L401）， onboarding UI 条件渲染（约 L567）
- `frontend/src/views/ArticlesView.vue` — `onLoad()` 未缓存文章列表
- `frontend/src/stores/playerStore.js` — `playArticle()` 中 `getArticleByUrl()` 调用（约 L230-241）
- `frontend/src/stores/queueStore.js` — 已正确使用 `localStorage` 持久化队列（不受影响，但配合修复使用）
- `frontend/vite.config.js` — PWA workbox 配置（L41-74）

## 修复方案

### 方案概述

采用"本地缓存兜底 + 离线状态感知"的策略，在不改变现有架构的前提下，让核心数据具备基础离线可用性。

### 具体修改

1. **feedStore 持久化订阅源列表**
   - `fetchFeeds()` 成功后将结果写入 `localStorage.setItem('jasmine_feeds_cache', JSON.stringify(data))`
   - `fetchFeeds()` 失败时（尤其是网络错误），若 `localStorage` 中有缓存，则返回缓存数据并打印 warning，不再抛出错误
   - 切账号时自动清除旧账号缓存

2. **FeedView / ArticlesView 持久化文章列表**
   - `onLoad()` 成功返回文章后，将 `articles` 数组写入 `localStorage.setItem('jasmine_articles_cache', JSON.stringify(articles.value))`
   - 页面初始化时，如果 `navigator.onLine === false` 且 API 加载失败，从 `localStorage` 恢复上一次的文章列表
   - 增加离线提示 Toast：若处于离线状态且加载失败，提示"当前无网络，显示已缓存内容"

3. **FeedView 离线 UI 修正**
   - 引入 `useNetworkStatus()` 检测网络状态
   - 修改 onboarding 显示条件：仅当 `hasFeeds === false && 网络正常` 时显示新人引导。离线状态下即使文章为空也显示空状态（带网络异常提示），避免误导用户

4. **playerStore 离线播放容错**
   - 在 `playArticle()` 中，若文章 `content` 为空且设备离线 (`navigator.onLine === false`)，直接 Toast 提示"当前无网络，无法获取完整文章内容"并返回，不再发起失败的 API 请求
   - 若文章 `content` 为空但在线，保持现有逻辑尝试获取

5. **ListenView 离线兼容性**
   - 已验证 `queueStore` 使用 `localStorage` 持久化，离线时队列数据本身不会丢失
   - 配合 Feed/Articles 缓存修复后，用户可正常查看和操作已缓存的播放队列

## Codex Review Decisions

### problem 1: 跨账号数据泄漏（全局文章缓存 key）
✅ 接受 — 已将 `FeedView.vue` 中的 `jasmine_feed_articles_cache` 改为按 `用户ID + feed_id + sortField + sortDirection` 生成隔离 key，并在 `authSessionReset.js` 登出时清除所有 `jasmine_feed_articles_cache_` 前缀的缓存，避免切账号后泄漏旧用户数据。

### problem 2: 不同查询条件下的缓存错位
✅ 接受 — 文章缓存 key 已包含当前筛选条件（`feed_id`、`sortField`、`sortDirection`），离线时仅恢复与当前视图匹配的缓存，不会出现"All Sources"加载到上次筛选标签数据的问题。

### problem 3: `removeFeed` 后本地缓存未同步
✅ 接受 — 在 `feedStore.removeFeed()` 删除成功后，立即调用 `saveFeedsToCache()` 更新 `localStorage`，避免离线重启时复活已删除的订阅源。

### problem 4: 文档与实际修改不一致
✅ 接受 — `ArticlesView.vue` 实际上未修改，已将文档中修复文件列表和修复记录对齐到真实变更文件（`FeedView.vue`、`feedStore.js`、`playerStore.js`、`authSessionReset.js`），并更新修复状态勾选为已完成。

## Review意见

- problem 1:
  - level: p0
  - angle: [Boundary][Security]
  - location: `frontend/src/views/FeedView.vue:39`, `frontend/src/views/FeedView.vue:229`, `frontend/src/utils/authSessionReset.js:13`
  - description: `jasmine_feed_articles_cache` is stored under one global key, and the new auth-reset flow never clears it. After user A logs out and user B logs in on the same device, opening Feed while offline can restore user A's cached articles into user B's session. This is a cross-account data leak, not only a stale-UI issue.
  - fix suggestion: Scope article cache by stable user id and clear all article cache entries during `resetAuthSessionState()` / logout. If the cache must survive reloads, the key should at least be namespaced by user id.

- problem 2:
  - level: p1
  - angle: [Implicit Assumption][Boundary]
  - location: `frontend/src/views/FeedView.vue:39`, `frontend/src/views/FeedView.vue:173`, `frontend/src/views/FeedView.vue:229`
  - description: The offline article cache assumes one cached list can safely back every Feed view. The page actually has different query shapes (`feed_id`, sort field, sort direction, pagination progress). If the user last cached a filtered tab, then reopens "All Sources" or another tab offline, the code will inject the wrong dataset while the UI still shows the current filter state.
  - fix suggestion: Include the active query fingerprint in the cache key or cached payload, such as user id + `feed_id` + sort settings + page coverage, and only restore entries that match the current view.
  - decision and reason(by claude):

  - fix suggestion: Persist the updated `this.feeds` array after deletes and any other feed mutations, or centralize cache writes so every mutation path keeps memory and localStorage in sync.
